## Connected production behavior

`main.rs` routes the auth group through the normal `fanbox_auth::prepare_root` and `fanbox_auth::Data` composition. Parsing and UID stdin resolution occur at their captured root boundary; startup hooks run before the applicable leaf. Sparse auth operations do not call `ensure_defaults` or eagerly load FANBOX runtime settings. The service factory opens the real local database and sparse Store only when the leaf reaches that dependency. Options are loaded lazily when the default session opener is needed; an injected valid-string session opener retains Go's options/proxy bypass.

The new `ConfigFiles` protocol is the normal production counterpart of Go `Store.Files`, with path/read/private-write/ensure operations and a real system implementation. It supports genuine file-boundary fault comparison without a test-only production branch. FANBOX default mutations preserve comments, unrelated Pixiv auth, unknown keys and existing sparse content; an absent default can be cleared without initializing network/runtime defaults. Invalid unrelated runtime settings do not block operations that only read or change the FANBOX default.

Import validates identity before saving, persists the session as an opaque BLOB, increments an existing credential revision without changing sort order/created-at, then reads/sets/rechecks the default. A later config failure leaves the already committed account intact, as in Go. Explicit default removal remains blocked; automatic selection uses stored order without renumbering after removal. Rotation distinguishes missing account from stale revision. Typed SQLite, SDK, config and context causes remain discoverable through the app/CLI error wrappers.

Import/browser uses the command context; list/status/use/remove use the captured background-context boundary. JSON output omits credentials and private browser paths. Text output retains ignored-writer-error behavior, JSON retains single-write/nil-short-write semantics, and explicit `--json=false` still requests the machine error envelope. Cleanup occurs after presentation and joins a command failure before the database-close error; the normal main owner consumes its database once.
